Describe a row with a struct

A struct is a named group of fields, each with a type. Think of one row of a table with its column types written down. A Vec of them plays the part of a DataFrame's rows. (If you've met Python's @dataclass, a struct is that, except the types are checked when the program is compiled.)

{{code:t1_struct#struct}}

Pick each field's type from the column:

  • INTEGER becomes i64, a 64-bit signed integer. SQLite's integers are 64-bit, so i64 always fits.
  • TEXT becomes String: text that the struct owns. You'll see its cousin &str in a moment.
  • A column that can be NULL becomes Option<T>. Option<String> is either Some(text) or None. Rust has no null, so a missing value has to be visible in the type, and the compiler makes you handle it before you use it.

Load the rows

Here is the whole load step, with main:

Line by line:

  • db.prepare(...) compiles the SQL once and gives back a statement. It can fail (a typo in the SQL, say), so it returns a Result, and the ? passes any error up to the caller.
  • stmt.query_map([], |row| ...) runs the query and calls the closure |row| ... once per row. A closure is an inline function, like Python's lambda but allowed to be as long as you like. The [] means "no parameters".
  • The closure ends in Ok(Loan { ... }) because query_map wants each row's answer as a Result: a loan, or the error that stopped it. A ? inside a closure returns from the closure, not from load_loans. It ends that one row's call with the error, and query_map passes the error on.
  • row.get(0)? reads column 0 and converts it to whatever type the field needs. The compiler works out the type from the struct field. If the conversion fails, for example a NULL going into a String, you get an error, not a silent empty string.
  • rows.collect() runs through every row and gathers the results. The function's return type, rusqlite::Result<Vec<Loan>>, tells collect what to build: either every row in a Vec, or the first error.
  • fn main() -> Result<(), Box<dyn Error>> lets main use ? too. On success it returns Ok(()), where () is Rust's "nothing". On failure it returns an error, and Rust prints it and exits with a failure code. For now, read Box<dyn Error> as "any kind of error". Ticket 6 explains what dyn means, and ticket 5 replaces it with an error type of your own. For a program this size, it is enough error handling.

Work on the rows

A Vec<T> is Rust's growable list, the equivalent of a Python list whose items all have one type. To count loans that are out:

{{code:t1_filter#count}}

.iter() walks the items one at a time without changing or consuming them. .filter(...) keeps the items its closure says yes to, and .count() counts them. Nothing runs until count asks for items. These chains are called iterator adaptors, and they're how most Rust code works through collections. The same thing as a loop:

{{code:t1_loop#loop}}

Both compile to essentially the same machine code. Use whichever reads better. Here the chain does: it says "count the out loans" in one line. In Python the chain is sum(1 for loan in loans if loan.status == "out"), and in pandas it's (df.status == "out").sum(). filter does the job of a boolean mask.

Closures can do more than |x| x + 1. Four things you'll see from here on:

{{code:t1_closure#closures}}
{{out:t1_closure}}
  • A closure can use the variables around it. This is called capturing. fine_per_day isn't a parameter, but the closure can read it.
  • |_| takes an argument and ignores it. || takes no arguments at all. unwrap_or_else(|| ...) calls its closure only when there's no value, so the format! doesn't run when it isn't needed.
  • The name of a function is a value you can hand over, without the parentheses. .map(String::from) is the same as .map(|s| String::from(s)).

Borrowing, in five minutes

Look at the parameter: loans: &[Loan], not loans: Vec<Loan>. The & means count_out borrows the loans: it can read them, and the caller still has them afterward. This is the idea that makes Rust Rust, so here is what happens without it:

{{fail:t1_move}}
{{failout:t1_move}}

Every value in Rust has exactly one owner. Passing a Vec by value moves it: total_len owns it now, frees it when it returns, and main can't touch it again. Python never has this problem because every variable is a shared reference and a garbage collector cleans up. Rust has no garbage collector. It frees memory at a moment the compiler can see, and ownership is how it sees that moment.

You have three choices whenever a function needs a value:

  • Borrow it (&[Loan], &Loan, &str) when the function only reads. This is the default. Nearly every function you write this week should take its input this way.
  • Borrow it mutably (&mut Vec<Loan>) when the function changes it in place, like sorting.
  • Move it (Vec<Loan>) when the function keeps it or consumes it. Or .clone() it first if you need your own copy, which costs a full copy, every time.

Write &[Loan] rather than &Vec<Loan>. A slice, &[T], is a view of some items in a row, and it accepts a borrowed Vec, an array or part of either. Clippy will tell you this too.

There is one rule for borrows, and the compiler checks it everywhere: a value can have any number of & borrows, or exactly one &mut, but never both at once. Many readers, or one writer. Here a reference is still in use when the code tries to change the list:

{{fail:t1_borrow}}
{{failout:t1_borrow}}

The reason is concrete. When a Vec is full, push gets a bigger block of memory, may copy every item across to it, and gives the old block back (under the hood shows this happening). first would still point into the old block, at memory that's no longer the list's. Python can't get into this state, because its garbage collector keeps anything alive while something points at it. C can: the same program compiles and reads whatever is in that memory now. A borrow lasts until the last line that uses it, not to the end of the block, so moving the println! above the push fixes it: first is finished with by then.

  • sort_by_key sorts by whatever the closure returns. Sorting changes the Vec, so the variable must be declared let mut. Rust variables can't be changed unless they say so, which is why the error in set up happened.
  • The sort is stable: items with equal keys stay in their old order. After the first sort, "pear" still comes before "kiwi" because it did before.
  • A tuple key, (w.len(), *w), sorts by the first part, then breaks ties with the second. Python's key=lambda w: (len(w), w) is the same idea.

Write a file

{{code:t1_write#write}}

Called with the sorted loans from the example above:

{{code:t1_write#call}}
{{out:t1_write#1}}
  • File::create makes or empties the file. BufWriter collects your small writes in memory and hands them to the operating system in big chunks. Without it, every writeln! is a separate request to the OS, which is much slower.
  • writeln! works like println!, but into anything you can write to. Writing can fail (disk full, no permission), so it returns a Result and needs a ?.
  • flush pushes out whatever is still buffered. A BufWriter also flushes when it's dropped, but it has to ignore errors when it does that. Flushing yourself means an error reaches you.
  • std::io::Result<()> is the I/O module's own Result, a type alias like rusqlite's, with its error type filled in.
  • use std::io::Write is there because writeln! into a file and flush come from Write, a trait: a named set of methods that many types share (ticket 3 explains traits). A trait's methods only work where the trait is imported. Forget the line and the error says "items from traits can only be used if the trait is in scope", and its help gives you the use line to add.

Under the hood

Where your data lives: the stack and the heap

A running program gets memory in two places. The stack holds each function's local variables. It is fast, because making room is just moving a pointer, and limited: every value on it must have a size known when the program is compiled. The heap is a big pool for anything else. You ask for a block of any size while running, and someone has to give it back.

A Vec is both. A Vec in a local variable is three numbers on the stack: a pointer to a block on the heap, how many items are in it (length), and how many fit before it needs a bigger block (capacity). The items themselves sit side by side in that heap block. A String has the same three numbers, pointing at bytes of text.

You can measure this yourself:

{{code:t1_memory#sizes}}
{{out:t1_memory#1}}

A String is 24 bytes whether it holds "Ada" or a novel: the text is elsewhere. And Option<String> costs nothing extra. Some bit patterns can never be a valid String (its pointer is never null, for one), so Rust uses one of those patterns to mean None. The spare pattern is called a niche.

When a Vec runs out of room, it asks the allocator for a bigger block, and today's implementation roughly doubles it. The standard library doesn't promise the factor. The allocator may grow the block where it is, or hand back a new one and copy everything across. Pushing 2,017 IDs one at a time:

{{code:t1_memory#growth}}
{{out:t1_memory#2}}

Ten trips to the allocator for 2,017 pushes. Growing by a constant factor means the total copying is at most a small multiple of the final size, so a push costs a constant amount on average, even though the occasional push may copy everything. That's called amortized O(1). O(1), said "order one", means the cost doesn't grow as the list grows; ticket 3's under the hood explains the notation properly. It's the same reason Python's list.append is fast. If you know the size up front, Vec::with_capacity(n) skips the copying entirely. Ticket 8 measures whether that matters.

Moves now make sense too. Moving a Vec copies its 24 bytes and leaves the heap block where it is. What must never happen is two owners both freeing the same block, and that is the mistake the move error stopped.

Why the dates sort as text

{{code:t1_dates#dates}}
{{out:t1_dates}}

Text compares character by character, left to right, and the first difference decides. That's lexicographic order, the way a dictionary is ordered. A YYYY-MM-DD date puts the most significant part first and pads every part to a fixed width, so text order and time order agree. 8/11/2026 breaks both rules, and so it sorts before September 2025. This is why ISO 8601 exists, why your logs and filenames should use it, and why ticket 4, where the dates aren't ISO, needs a real date type.
