Group by, without SQL

In SQL this is a GROUP BY. In pandas it's df.groupby("supplier_id")["amount"].agg(["count", "sum"]). In Rust you do it yourself with a HashMap, and once you've done it you'll recognize it inside every groupby you ever call.

A map from keys to values

HashMap<K, V> is Python's dict, with one key type and one value type. It lives in std::collections, so it needs a use:

get doesn't return the value. It returns an Option: Some(value) if the key is there, None if it isn't. Python's d[key] raises KeyError at run time. Rust makes "the key might not be there" part of the type, so you decide what happens before the program ever runs. Try to skip that decision and the compiler stops you:

The suggested .expect("REASON") would compile. It means "crash with this message if the key is missing". That's right when a missing key would be a bug in your program, and wrong when it's something the data can do. Most of the time you want one of these:

  • match handles both cases and says what each one does.
  • if let Some(n) = ... is match when you only care about one case.
  • .copied().unwrap_or(0) turns "maybe a reference to a number" into "a number, or 0". copied turns Option<&u32> into Option<u32>. Look up Option in the docs and skim its methods. You'll use a dozen of them by ticket 6.
  • map[&key] also works. It panics if the key is missing, just like Python's d[key]. Use it only where a missing key really is impossible, and you can say why.

Counting and summing: the entry API

The core of every group-by is "find this key's running total, or start one at zero, and add to it". The entry API does that in one lookup:

{{code:t2_map#entry}}
{{out:t2_map#3}}

counts.entry(w) finds the slot for w. .or_insert(0) fills it with 0 if it's empty and hands back a mutable reference to the value, and the * in front reaches through that reference so += 1 changes the number in the map. .or_default() does the same with the type's default, which is 0 for numbers. Python's version is counts[w] = counts.get(w, 0) + 1, or Counter.

A HashMap has no order. To print or write one predictably, collect it into a Vec and sort that. counts.into_iter() walks the map by value: each item is an owned (key, value) pair, and the map is used up, so you can't touch counts afterward. counts.iter() would borrow instead and hand out references, the way for x in &list does. More on why under the hood.

Owned text and borrowed text

Look at the key type: &str, not String. That choice matters more than it looks.

  • String owns its text on the heap. You can keep it as long as you like, change it, and hand it to someone else.
  • &str is a borrowed view of text that somebody else owns: a pointer and a length. It costs nothing to make, but it's only valid while the owner is alive and unchanged.

When your rows are already loaded into a Vec, a map keyed by &str borrows names straight out of those rows, and nothing is copied. A map keyed by String needs its own copy of every key, made with .clone() or .to_string(). For a map that's built, used and thrown away in one function, borrow. For a map that has to outlive the rows it came from, own. The compiler holds you to it:

{{fail:t2_drop}}
{{failout:t2_drop}}

per_shelf holds views into books, so books can't be thrown away while per_shelf is still in use. The same program in C would compile, then read freed memory and maybe print garbage. Python never has the problem, because its garbage collector keeps the strings alive as long as anything points at them. Rust rejects it before it runs. Ticket 3 gives this rule its proper name.

The same thinking applies to function parameters. Take &str when you only read text, because a &String turns into a &str automatically and a string literal already is one.

Sorting by a float

The sort line uses total_cmp, not sort_by_key. Here's why:

{{fail:t2_sortf64}}
{{failout:t2_sortf64}}

sort_by_key needs a key that implements Ord, a total order, where any two values compare as less, equal or greater. Floats don't have one, because of NaN ("not a number", what 0.0 / 0.0 gives you). NaN is not less than, equal to or greater than anything, itself included. Python sorts floats anyway and quietly gives you a wrong order if a NaN sneaks in. Rust makes you choose. a.total_cmp(&b) is a total order on floats that puts NaN at the ends, which is what you want for sorting. .then_with(|| ...) breaks ties with a second comparison, just like the tuple keys in ticket 1.

Formatting money

The output above prints each total twice: {total:>6.2} right-aligns it in six characters with two decimals, and plain {total} prints the shortest decimal that reads back as exactly the same float. On this tiny library they agree. On a quarter's invoices they won't, and you'll see digits like ...55000000002. That's not a bug in your code: it's what floating point does. For this report, format with two decimals and move on. Ticket 3 is where it stops being cosmetic.

If you choose the placeholder and write names.get(&id).copied().unwrap_or(&format!(...)), the compiler says "temporary value dropped while borrowed". format! makes a new String that nothing keeps, so it's freed at the end of the statement, and the &str you borrowed from it can't outlive it. One way out is to make the name owned at the point where you write each output row: one String per supplier row is a couple of dozen small copies at most, which is nothing. Under the hood

How a hash table finds things

A HashMap is an array of slots called buckets. To store a key, it runs the key through a hash function, which turns any value into a big number that looks random but is always the same for the same key. Then it uses part of that number to pick a bucket. To find the key again, it hashes it again and looks in the same place. No searching, so lookups take about the same time with ten keys or ten million: O(1) on average.

{{code:t2_hash#hash}}
{{out:t2_hash}}

Two keys can land in the same bucket. That's a collision, and every hash table has a plan for it: look in the next free slot, or keep a little list per bucket. Collisions are why the table keeps spare room. When it gets too full (Rust's table grows when it's seven-eighths full), it allocates a bigger array and moves every key, the same doubling trick as Vec. Rust's HashMap is a port of Google's SwissTable design, which checks sixteen slots at a time with single CPU instructions.

Why the order changes every run

The example above used DefaultHasher::new(), which always hashes the same way, so its output is the same every time. A real HashMap doesn't. Each one gets a hasher with secret random keys, seeded from the operating system. So the same names land in different buckets on different runs, and iterating the map gives a different order.

This is deliberate. If a web server's hash function is fixed and public, an attacker can send thousands of keys built to land in one bucket, and every lookup becomes a slow search through all of them. That's called hash flooding, or HashDoS. In 2011 researchers showed it working against most of the popular web platforms of the day. A secret random key per map stops it, and the hash Rust uses, SipHash, was designed so the keys can't be worked out from outside.

The lesson for your reports: never let output order depend on a HashMap. Sort first. Python's dict keeps insertion order, which hides this habit until you work in a language that doesn't.

Sorting, and what stable means

Comparison sorts, the kind that work by asking "is a before b?", need about n log n comparisons for n items, and it's been proved that none can do better in general. For a report of a couple of dozen rows that's nothing. For ten million rows it's the difference between seconds and hours, compared with a naive sort that needs n².

sort, sort_by and sort_by_key are stable: equal items keep their original order. Since Rust 1.81 they use a merge sort variant called driftsort. sort_unstable and friends can reorder equal items, use no extra memory, and are often faster. Stability matters when you sort twice: sort by name, then stable-sort by total, and suppliers with equal totals stay alphabetical. Your tie-break with then_with gets the same result in one sort, and it says so in the code.
