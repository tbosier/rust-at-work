How this works

Kettle Creek Supply buys parts from two dozen suppliers and sells them to factories and repair shops. Purchasing raises a purchase order (PO) for each order: what it bought, how many and at what price. The supplier ships the parts and later sends an invoice, which says how much to pay. Most of the work in this course comes from a single question that every distributor asks: did we pay what we agreed to pay?

The company is invented and so is every row of its data. The work is real. Reconciling invoices, cleaning a newly acquired branch's records, building a scheduled job and putting an API in front of it are things people get paid to do, and they need the same skills here as they do in a real job.

House rules

These are the rules a good engineering team would give a new hire. Each one is here because breaking it costs you something later.

  1. You write every line. Claude can explain a compiler error, point you at a concept, or review finished work. It does not write your implementation. The CLAUDE.md you add during set up tells it so.
  2. SQL stops at SELECT columns FROM table. No WHERE, JOIN, GROUP BY or SUM. Kettle Creek's IT team asks for this because business rules buried in SQL strings inside a program are easy to miss in review, awkward to test without a live database, and soon forgotten. For you there is a second reason: every filter, join and total you write in Rust is Rust you learn.
  3. No crate until a ticket needs it. Each ticket names the crates it allows. Learning what the standard library already does is part of the job.
  4. Clean before review. cargo fmt, then cargo clippy --all-targets with no warnings, then cargo test. A reviewer's time goes on design, not on things a tool can find.
  5. Commit each ticket, and say why. A commit message says what changed and why it changed. Tag the commit you hand in, so the review can see exactly what changed since the last ticket.
  6. Keep a journal. Three lines per ticket in JOURNAL.md: what surprised you, what the compiler taught you, and what you would design differently. Writing it down is what turns an error you fixed into one you won't make again.

Set up

Do this before week zero. The point is a project you can build, a loop you can run in your sleep, and the rules written down where Claude will read them.

Check your tools

cargo --version
rustup component list --installed

You want cargo 1.89 or newer (rustup update gets it) and, in the component list, clippy, rustfmt and rust-analyzer. On this machine all three are installed.

Make the project

cd ~/projects
cargo new kettle_creek
cd kettle_creek
mkdir data out
cp ~/projects/space_sim/learning/data/kettle_creek.db data/   # or wherever your copy is
cargo add rusqlite --features bundled
printf '/out\n/data/*.db\n' >> .gitignore

cargo new makes Cargo.toml, src/main.rs and a git repository with a .gitignore that already skips target/. The last line adds two more: your program's output files, which are rebuilt every run, and your copy of the database, which you can always copy again.

cargo add rusqlite --features bundled adds the SQLite crate. A crate is one unit of compiled Rust, a library or a program, and a package is what cargo downloads and builds, holding one or more crates. Day to day, people say crate for both. bundled compiles SQLite itself from C source into your program, so SQLite doesn't have to be installed on the machine. It does need a C compiler. On Linux and macOS, Rust normally links programs through the system's C toolchain, so you usually have one already. If the first build fails with an error that mentions cc, install your system's C build tools and try again. That makes the first build slow, a minute or so, and every build after it fast. Cargo.toml now ends with something like:

[dependencies]
rusqlite = { version = "0.40.2", features = ["bundled"] }

Your version may be newer. If an example on this page stops compiling with a newer rusqlite, pin the tested one with version = "=0.40.2".

Your editor

Whatever editor you use, it should run rust-analyzer, the program that reads your code as you type and shows errors, types and docs in place. Without it you find every mistake at the next cargo build, and Rust is much harder to learn that way.

Your Neovim already runs rust-analyzer through rustaceanvim, with clippy on every save, and shows inferred types as gray inlay hints. Start nvim from the project folder so it picks up the right project. The keys worth learning this week, all from your own config. <leader> is the prefix key your config sets. With a different Neovim setup the keys will differ, and the actions are what to look for:

KeyWhat it does
KHover: the type and docs of whatever is under the cursor. Use it constantly.
gdGo to definition, including into a crate's source. Reading library code is how you learn idioms.
<leader>cdShow this line's problems in a float.
<leader>rdThe full compiler message, laid out the way cargo build prints it. Read this rather than the one-line summary.
<leader>reExplain the error code, the same text as rustc --explain.
<leader>roOpen the docs page for the symbol under the cursor.
<leader>rr, <leader>rtRun the program, run tests.
<leader>xxEvery problem in the project, as a list.

If you'd rather use VS Code, install the rust-analyzer extension (from the rust-lang publisher) and open the project folder, not a single file. Then set rust-analyzer.check.command to clippy in the settings, so you see clippy's warnings on every save. The same jobs, VS Code's way:

How to read a compiler error

Rust's compiler is the best teacher you'll have, if you read what it says. Here is a small mistake and the message it produces:

{{fail:t1_mut}}
{{failout:t1_mut}}
  • The first line is the headline: an error code (E0596) and a sentence. The code is a search term: rustc --explain E0596 prints a page about it with examples.
  • The arrow (--> src/main.rs:3:5) is the file, line and column.
  • The carets (^^^^^) underline the exact code, with a label saying what is wrong there.
  • The help is a suggested fix, and the +++ marks what it would add. It is right most of the time. When it isn't, it still tells you what the compiler expected.

Fix the first error, then rebuild. One mistake often causes several errors further down, and they disappear with the first.

Tell Claude the rules

Save this as CLAUDE.md in the project root. Claude Code reads it at the start of every session in that folder, so the rules hold even when you ask for help late at night and would secretly like the answer.

# kettle_creek

My Rust learning project. I am working through the guide at
~/projects/space_sim/learning/rust_at_work.html, one ticket at a time.

## Rules for Claude

- Never write or edit code in this project, even if I ask casually.
  Never show me a full solution to a ticket.
- If I'm stuck, ask what I tried, then give the smallest hint that
  unblocks me: a concept name, a docs link, or a short example on
  different data. Suggest the next rung of the guide's hint ladder
  before going further.
- Explaining compiler errors is encouraged: what the message means and
  what Rust is protecting me from. Let me write the fix.
- When I ask for a senior review, follow "How reviews work" in the
  guide: run the checks, compare my output with the answer key, then
  review like a senior engineer on a pull request. Don't rewrite it.
- The answer key is in ~/projects/testRandomShiz/rust_at_work/answer_key.
  Never show me its code or open its output files for me. You may compare
  my output with it and tell me where they differ.

Then start the journal and make the first commit:

printf '# Journal\n\n' > JOURNAL.md
cargo run
git add -A
git commit -m "Start kettle_creek: empty binary, rusqlite, rules for Claude"

If cargo run prints Hello, world! after compiling SQLite, you're set up. Week zero is next.

How reviews work

A review is where most of the learning in this course happens. Getting a program to print the right number is half the job. The other half is a program that the next person, or you in six months, can read, change and trust. Nobody can teach you that half from a book. It comes from someone looking at your code and asking why.

When to ask

When the sanity checks pass, cargo fmt and cargo clippy --all-targets are clean, and the work is committed and tagged:

git add -A
git commit -m "Ticket 1: count open POs and list stale ones"
git tag t1-submitted

What to paste

Start claude in the project folder and paste this, with the ticket number filled in. Each ticket adds a line or two of its own to focus the review.

Senior review, ticket N.

My code is in this folder; the tag tN-submitted is what I'm handing in,
and the ticket is the "Ticket N" section of
~/projects/space_sim/learning/rust_at_work.html.

1. Run cargo fmt --check, cargo clippy --all-targets and cargo test,
   then run the program the way the ticket asks.
2. Compare my output files with the answer key's
   (~/projects/testRandomShiz/rust_at_work/answer_key/out/tN/).
   Tell me whether they match. If not, tell me which rows or numbers
   differ, but not why. Free-text columns (like a reject reason) only
   have to mean the same thing, not match word for word.
3. Review it like a senior engineer reviewing a pull request:
   correctness, structure and file layout, naming, error handling,
   ownership, idiomatic Rust and tests. At most seven points, most
   important first. For each one: file and line, what's wrong, why it
   matters, and the concept or docs page to look up.
4. Don't rewrite my code or show me a fixed version. A short example on
   different data is fine.
5. End with one thing I did well, and one question for my journal.

What the reviewer looks for

The same list every time. Read it before you start a ticket, not just before you hand it in.

AreaThe question
CorrectDoes it do what the ticket says, including the edge cases the email mentions in passing?
ClearDoes main read like a summary of the program? Does each function do one thing its name describes?
StructuredIs each file about one thing? Is the structure as simple as the problem allows, and no simpler?
Honest about failureCan bad data or a missing file crash it? When it fails, does the message say what went wrong and where?
OwnershipDoes it borrow by default, and clone only on purpose?
IdiomaticIterators where they read better than loops, the standard library's types instead of homemade ones, derive instead of hand-written boilerplate.
TestedFrom ticket 4: would a test fail if the important logic broke?
ReproducibleSame input, same output, byte for byte. No absolute paths baked in.

After the review

Fix what it found, yourself. If you disagree with a point, say so and ask for the tradeoff. A good reviewer can tell you what the alternative costs, and sometimes your way is fine. Then write your journal lines, commit, and git tag tN-final. The next ticket starts from there.
