A codebase a stranger can work on

Your src/main.rs holds four tickets now. It works, and you can find your way around it because you wrote it. This page is about turning it into a small library with a thin program on top, so that someone else can find their way around too, and about doing that without changing a single byte of output.

Change the shape, not the behavior

Changing the structure of code without changing what it does is called refactoring. The danger is obvious: you move two hundred lines and something small breaks without anyone noticing. So before you move anything, save what the program produces today, and after every step, check that it still produces exactly that:

cargo run > ../printed_before.txt
cp -r out ../out_before

# move one thing, then:
cargo run > ../printed.txt && diff ../printed_before.txt ../printed.txt && diff -r ../out_before out && echo "no change"

The .. puts the saved copies in the folder above your project, outside the repository, so nothing git does to your project can touch them. cargo run > ../printed.txt saves what the program prints, so the counts and totals on screen are checked too, not just the files. diff compares two files and diff -r two folders, file by file, and both print nothing when they match. && runs the next command only if the one before it succeeded, so "no change" appears only when the program ran and everything matched. If something did change, you know which step did it, because you only took one. Commit after each step that passes. Then a step that goes wrong costs you two commands. git restore . puts every file git already tracks back the way it was at the last commit, as long as you haven't run git add since. New files the step created, like a fresh src/lib.rs, aren't tracked yet, so it leaves them. git clean -nd lists them, new folders like tests/ included, and git clean -fd deletes them. Ignored files, like out/, are left alone by both, and the saved copies in .. are outside the repository altogether.

Do the two jobs in this ticket in order. Refactor first, until diff shows no change at all with everything in modules. Then add Millbrook to the reconciliation as a separate step, and expect exactly one file to change. Mixing them means a difference in the output could come from either.

This saved copy is a test. It can't tell you the output is right. It tells you the output didn't change, which is exactly the question a refactor asks. Under the hood says more about tests like this.

Modules: one file, one job

One package can hold a library and a program. src/lib.rs is the library: all the logic, organized into modules. src/main.rs is a thin program that uses the library by the package's name, the way any outside code would. Here is the main.rs of a tiny example project called shelf, whose library has one module, duration, holding ticket 4's parse_duration:

use shelf::duration::parse_duration;

fn main() {
    for raw in std::env::args().skip(1) {
        match parse_duration(&raw) {
            Ok(days) => println!("{raw}: {days} days"),
            Err(e) => eprintln!("{raw}: {e}"),
        }
    }
}

You don't need to build shelf. Read its files here; the drills below make the same moves in your snippets project, and then you make them for real in kettle_creek. In your project the first part of every such path is kettle_creek, the name in your Cargo.toml. Two keywords do two different jobs, and Python folds both into import:

  • mod declares that a module exists. pub mod duration; in lib.rs tells the compiler to read src/duration.rs as a module named duration. Each module is declared exactly once, in its parent. In Python every file is a module automatically. In Rust a file that no mod line mentions is never compiled at all.
  • use makes a short name for something that already exists. use crate::money::Cents; lets the rest of that file write Cents instead of the full path. Write use lines in any file that needs them. Inside the library, paths start with crate, meaning "this library". From main.rs and from tests, they start with the package's name.

That privacy is a feature. A module's pub items are its promise to the rest of the code, and everything else can change without breaking anyone. Make things pub when another module needs them, not by default. pub(crate) means "visible inside this library, but not to outside code", and outside code includes your own main.rs. Making a struct pub doesn't make its fields pub. Each field needs its own, which is what made ticket 4's CardNumber safe.

Start each file with a //! comment, one sentence on what the file is for. That kind of comment documents the module it's in, and cargo doc shows it on the module's page. If the sentence needs an "and", the file may be two files. Move one module at a time and run cargo check after each move. The compiler lists every use and pub you missed, which turns a scary refactor into a checklist.

One error type for the library

Since ticket 1 your functions have returned Box<dyn Error>: any kind of error, with its exact type forgotten. That suits main, which only prints errors. A library's callers sometimes need to know which error it was. A missing database file and a corrupt one need different fixes, and a test may want to check that the right error came back. An enum keeps that information. The catch is that a function which reads the database and parses text can fail in two unrelated ways, and ? needs to know how to turn each one into the enum. Integration tests

Files in a tests/ folder at the project root are integration tests. Each one is compiled as a separate program that uses your library the way any outside code would, so it can only reach pub items. That makes it the right place to test a whole path, raw rows in and accepted rows plus rejects out, rather than one function.

use shelf::duration::{DurationError, parse_duration};

#[test]
fn a_whole_batch_of_slips() {
    let slips = ["14d", "2w", "", "3 months", "21 days"];
    let (good, bad): (Vec<_>, Vec<_>) = slips
        .iter()
        .map(|s| parse_duration(s))
        .partition(|r| r.is_ok());
    assert_eq!(good.len(), 3);
    assert_eq!(bad[0], Err(DurationError::Empty));
}

partition splits one iterator into two collections by a yes-or-no test, here the results that are Ok and the ones that aren't. In shelf, cargo test now runs four test programs:

{{out:t5_zz_tests}}

(Compile lines trimmed.) The unit tests inside the library, the binary's unit tests (it has none), the integration test, and doc-tests, which are code examples written in /// comments, compiled and run to check that the docs still work.

Notice what the integration test doesn't need: a database. If your Millbrook code takes a Connection and runs its own SELECT, every test has to build a database with the right table first. If it takes rows that were already loaded, as plain structs, a test can build three rows by hand. Code that's easy to test from outside usually has a clean interface, and the test is the first outside caller to find out whether yours does.

Under the hood

Information hiding

In 1972 David Parnas published a short paper, "On the Criteria To Be Used in Decomposing Systems into Modules". He took one small program and split it into modules two ways. The first followed the steps of the program, the way most people would: read the input, process it, write the output. The second gave each module one design decision that was likely to change, and hid that decision behind the module's interface. Then he asked what each version would cost to change. In the first, most changes touched most modules, because every step knew how the data was stored. In the second, most changes stayed inside one module.

That's the test to put to your own layout. Next year Millbrook might send CSV files instead of a table. Priya might want a dispute status on each discrepancy. Money might need a currency. For each change, count the files you would have to open. If db.rs is the only file that knows the data lives in SQLite, a new source of rows changes one file and adds another. If Cents keeps its i64 private, the day it needs a currency field, nobody outside money.rs notices.

John Ousterhout's word for a good module is deep: a small interface with a lot of work behind it. parse_amount(&str) -> Result<Cents, AmountError> is deep. It's one function with one input, hiding signs, commas, parentheses and the cents rule. A module that makes every helper pub is shallow, because its callers have to learn everything it knows.

What cargo actually compiles

The Rust compiler, rustc, works on one crate at a time. A crate is the unit of compilation: rustc starts at lib.rs or main.rs, follows every mod line to the files they name, and compiles the whole tree as one piece. Modules are walls and names inside that piece. Python works differently: it compiles each file separately, when the running program first imports it.

Your package now holds several crates. Cargo compiles the library first. Then it compiles main.rs as a second crate that links to the library, and each file in tests/ as one more crate that does the same. That's why main.rs sees only what's pub: to the compiler it is outside code, exactly like a test. It's also why cargo test printed four sections above. Between builds, rustc keeps notes in target/ about what it already compiled (incremental compilation), so a one-line change doesn't redo everything. Big projects go further and split into many crates in a workspace, so cargo can compile independent crates at the same time and skip the ones that didn't change.

A diff is a test

Your ../out_before folder is what's called a golden file test: save output that's known to be good, and compare every new run against it. Michael Feathers calls tests like this characterization tests, in Working Effectively with Legacy Code. They pin down what code does today, right or wrong, so you can change it safely. They're cheap to write and catch any change at all, which makes them the right tool for a refactor. A bug fix is different: it's supposed to change the output, and the old golden file can't tell a fix from a mistake. There you read the new output, check the change is the one you meant, and save it as the new golden file. They're brittle too, when output contains something that changes every run, like a timestamp. Ticket 6's workbook has one. Unit tests say why each rule exists. A golden file says only that nothing moved, and during a refactor that's the one thing you need to know.
