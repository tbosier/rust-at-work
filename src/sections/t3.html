Make wrong answers hard to write

Ticket 2 was arithmetic. This one is judgment: every PO lands in exactly one of several outcomes, money has to be exact, and three tables have to be lined up against each other. Rust's answer to all three is the same idea: put the rules into types, so the compiler checks them every time you build. The library examples below have the same shapes as the ticket, on different data.

An enum for "exactly one of these"

An enum lists every possible form a value can take. Unlike a Python Enum, each variant can carry its own data:

A Standing is Lost, or Overdue with a number of days attached, or Out, or Returned. Never two at once, and never a value that isn't on the list. A string like "overdue" can be misspelled, and the misspelling compiles; Standing::Overdu does not.

You take an enum apart with match:

{{code:t3_enum#match}}
  • Standing::Overdue { days } matches the variant and pulls its days out into a variable, in one step.
  • if days > 30 after a pattern is a guard: the arm only matches when the condition holds too. Arms are tried top to bottom, so the 40-day loan takes the first Overdue arm and the 3-day loan falls through to the second.
  • A match is an expression. Each arm produces a value, and the whole match is the function's return value.

Why format!("{s:?}") inside the println!? A derived Debug doesn't pad the value as a whole: {:<26?} leaves Lost unpadded and pads the 3 inside Overdue { days: 3 }. So the line turns the value into a String first, and a String pads properly. matches!(value, pattern) is a one-line match that answers yes or no. Overdue { .. } means "the Overdue variant, whatever its fields are".

The rule that makes enums worth it: a match must cover every variant. Leave one out and the program doesn't build:

{{fail:t3_nonexhaustive}}
{{failout:t3_nonexhaustive}}

This is the compiler keeping a list for you. Add a variant next month and every match that forgot about it becomes an error you have to fix before anything runs. Python's match statement doesn't check this when it runs (a type checker can, if you set it up), and an if/elif chain simply falls off the end. A catch-all arm, _ => ..., turns the check off for that match. Sometimes that's right. In code that decides what to report, it means a new case gets silently reported as nothing.

What each derive buys you

The #[derive(...)] line asks the compiler to write standard behavior for your type. Each one is a trait, a named ability, that other code can rely on:

DeriveWhat you getWhy you'd want it here
DebugPrinting with {:?}Seeing what you have while you work
Clone, Copy.clone(); and with Copy, plain assignment copies instead of movingSmall values like a kind or an amount should behave like numbers. Copy is only allowed when every field is Copy, so not for a String
PartialEq, Eq== and !=Comparing kinds and amounts
PartialOrd, Ord<, .cmp(), .sort()For an enum the order is the order you declared the variants in. That's why Lost sorted first above

DefaultA zero value, T::default()What entry(...).or_default() starts from

Declaration order as sort order is worth noticing. If your report must list kinds in a set order, declare the enum's variants in that order and derive Ord: then sorting is correct by construction, and nobody has to keep a separate list of strings in step with the enum.

Indexes: find things without searching

Ticket 2 used a HashMap to add things up. Here it does its other job, an index: build it once, then jump straight to any item by its key. The map holds references into a Vec you already have, so nothing is copied:

{{code:t3_index#index}}
{{out:t3_index#1}}
  • HashMap<i64, &Book> maps a book ID to a borrowed book. Building it is one pass over books.
  • let Some(book) = ... else { ... }; is let-else. If the pattern matches, book exists for the rest of the loop body. If not, the else block runs, and it must leave: continue, return or break. It keeps the normal path flat instead of nesting it inside an if let. A cousin you'll meet when clippy suggests it: if done && let Some(day) = returned { ... } is a let chain, a condition and an if let in one if. It's new in Rust's 2024 edition, and fine to accept.
  • A HashSet<T> is a HashMap with keys and no values: a fast "have I seen this?". insert returns false when the item was already there, so one call both checks and records. A set's key can be a tuple, such as (i64, String), when "the same" means two fields at once.

map.get(&key) returns an Option, and Option has methods that save you writing a match each time:

Lifetimes, properly this time

Now the mistake everyone makes once: a helper that loads the books and returns the catalog.

{{fail:t3_dropped}}
{{failout:t3_dropped}}

books belongs to load_catalog, so it's freed when load_catalog returns. The catalog would point at memory that no longer holds books. In C this compiles and crashes later, or worse, doesn't crash and reads garbage. Rust refuses. There are two honest fixes:

  • Own the data higher up. Load the Vec in main (or whoever needs the answer), then build indexes that borrow from it. The data lives at the top, and everything below borrows. This is the usual shape, and the right one for this ticket.
  • Let the index own its data: a HashMap<i64, Book> with no references and no lifetime. Fine when the index is the only place the data lives.

The fix that isn't honest is .clone() sprinkled until the errors go away. It works, it copies everything, and it hides the question of who owns what, which is the question this ticket's design depends on.

Stuck?

Hint 1: two passes

Walk the invoices once, in invoice_id order, and you can settle the orphans and duplicates and add up what each PO was billed. Then walk the POs once and decide each one's kind from its status, its expected total and its billed total. Each pass is a single loop with index lookups inside it.

Hint 2: one row type for every kind

Every report row has the same columns, so make one struct for a row, with a field for the kind. The blanks are Options: expected: Option<Cents> is None on orphan and duplicate rows. Then difference doesn't need to be stored at all; it's a method that maps over expected.

The wiki's loan verdict is the shape: a tuple of the PO's status and billed.cmp(&expected). Guards can go on these arms too. If your status is still a String, that's a sign it wants to be an enum as well.

Under the hood

How a computer stores 0.1

An f64 is 64 bits in the IEEE 754 binary64 format: 1 bit for the sign, 11 for an exponent and 52 for a fraction. It's scientific notation in base 2, a number like 1.f × 2e, with about 15 to 17 significant decimal digits.

Base 2 is the problem. In base 10, 1/3 can't be written exactly: 0.3333... goes on forever, and you stop somewhere. In base 2 the same thing happens to 1/10, because 10 has a factor of 5 and powers of 2 don't. 0.1 in binary is 0.000110011001100110011..., repeating forever, so the computer keeps the nearest 53 significant bits and stores a number that is very slightly off. Print enough digits and you can see each one:

{{code:t3_float#exact}}
{{out:t3_float#2}}

0.1 is stored a hair high, and so is 0.2. 0.3 is stored a hair low. Add the first two and their errors don't cancel; the sum is rounded to a different nearest f64 from the one 0.3 got. Each step is correct to within half a unit in the last place, which is excellent for measuring a bridge. It's useless for "is this invoice exactly right?".

That was 508 mismatches in our own data, with plain f64 addition and == and the duplicates set aside. Done in integer cents, 401 of them disappear. Nearly four alarms in five would have been the float, not the supplier, and Priya's team would have spent a week learning to ignore the report.

Why rounding once at the boundary is safe: a stored price like 4.35 is really 4.349999999999999644..., within about one part in 1016 of what someone typed. Times 100 that's 434.99999999999994, a tiny distance from 435, so .round() lands on the integer you meant. That holds for amounts up to many billions of dollars. After that, integers add exactly: an i64 holds up to about 9.2 × 1018 cents. One warning: as i64 never fails. A float too big for an i64 becomes the largest i64, and NaN becomes 0. That's fine for numbers from a REAL column you've seen, and not for text from a stranger, which is why ticket 4 parses text straight into cents.

Floats are for measuring, estimating and deciding: averages, ratios, forecasts, the machine learning in Part 4. Money, counts and IDs are integers here (or a decimal type, where money has fractions of a cent).

Big-O, and the join you just wrote

Lining up two tables by a shared column is a join. There are two obvious ways to write one:

{{code:t3_join#joins}}

The first, a nested-loop join, searches the whole PO list for every invoice: with n invoices and m POs, about n × m comparisons in the worst case. The second, a hash join, makes one pass to build an index and one pass to look things up: about n + m steps, because a HashMap lookup takes the same time on average however big the map is (ticket 2's under-the-hood section is why). In big-O notation, the nested loop is O(nm) and the hash join is O(n + m). Big-O ignores constant factors and asks only how the cost grows as the input grows.

Here are both, timed on our real tables, then on copies made 4, 16 and 64 times bigger, built with --release:

{{out:t3_join_release}}

At today's size the difference is 0.4 milliseconds against 0.08, and nobody would notice. Each time the data grows 4 times, the hash join takes about 4 times longer and the nested loop about 16 times longer. That's what O(n) and O(n2) look like when you measure them. Carry the pattern on to the million invoices of ticket 8 and the nested loop takes minutes while the hash join takes a fraction of a second. These timings came from one desktop, an AMD Ryzen 9 5900X. Your milliseconds will be different. How they grow won't be, and that's why big-O is worth learning: it predicts the shape of a measurement you haven't made yet.

A debug build, plain cargo run, runs this sort of loop many times slower than --release. Never time anything in debug.

What a database index is

You aren't allowed to write a SQL JOIN, but it's worth knowing what one does. po_id is the INTEGER PRIMARY KEY of purchase_orders, so SQLite stores the table as a B-tree sorted by po_id: a shallow, wide tree that finds any key in a few steps, O(log n). A JOIN in SQLite is a nested loop. When the inner table has an index on the join column, as purchase_orders does on po_id, the inner loop becomes an index lookup instead of a scan, and that's how it stays fast without a hash table. Without a usable index it scans.

When you SELECT a table into a Vec, the index stays behind in the database. Your HashMap is the index you rebuild in Rust. The two make different trade-offs. A hash index is the faster of the two for "find this exact key", but it keeps no order. A B-tree keeps keys sorted, so it can also answer range questions, but only on the column it's sorted by. "Every PO between two dates" would need a B-tree index on order_date, which this table doesn't have. Rust has both: HashMap and BTreeMap. When you choose between them, you're making the same choice a database designer makes.
