Rust from the ground up

This page assumes you can program in Python and have never had to think about what happens underneath. Each new word is in italics where it's first explained, and the machine words (memory, addresses, processes) get a fuller explanation in under the hood at the end. Where Python does the same thing differently, the page says so, because the differences are where your instincts will mislead you.

You need a scratch project to type examples into. Make one next to where your work project will go:

cd ~/projects
cargo new snippets
cd snippets
cargo run

It prints Hello, world!. Type each example on this page into src/main.rs and run it with cargo run. An example with its own fn main is a whole program: replace everything in the file. An example without one is a piece. Lines that start with let, or that do something, go inside main, between fn main() { and its closing brace. Definitions (use, const, struct, impl, fn) go above main. Within one subsection, later pieces can use names from earlier ones, so keep the earlier lines, except a line that panics on purpose: delete that once you've seen it, or nothing after it will run. Type them, don't paste: your fingers learn the shapes that your eyes skim over. Ticket 1 adds a database library to this same project later.

What cargo run actually does

When you run python report.py, Python checks that the file is valid syntax, then carries out each line as it reaches it. A misspelled name or a wrong type on line 40 isn't noticed until line 40 runs. A typo in a branch that rarely runs can sit there for months.

Rust is compiled. A program called the compiler, rustc, reads all your source first, checks it, and translates it into machine code: the instructions your processor runs directly. The result is a file called a binary (or executable). cargo run is two steps: cargo build calls the compiler and writes the binary to target/debug/snippets, then cargo runs that file. You can run it yourself:

cargo build
./target/debug/snippets

Three things follow from this. Mistakes in types, names and spelling are found before the program ever runs, anywhere in the file, including in branches that rarely run. The binary runs without Rust installed, so you can copy it to another machine of the same kind (here, 64-bit Intel or AMD Linux with a similar system library) and run it there. And nothing changes until you build again: edit the source, forget to rebuild, and the old binary still does the old thing. cargo run always rebuilds what changed, which is why you'll use it most of the time.

The debug in the path is the build profile. A debug build compiles fast and keeps extra checks in. cargo run --release compiles slowly and makes a binary that's often many times faster, written to target/release/. Use debug while you write, and release when you measure speed or ship.

The compiler prints two kinds of message. An error stops the build: there is no new binary until you fix it. A warning doesn't: the program builds and runs, and the compiler is pointing at something that's probably a mistake. The two you'll see most in this page's examples are unused variable (you made a variable and never read it) and field is never read or function is never used, together called dead code. While you're typing examples piece by piece they're expected, because the next piece usually uses the thing. In real work, read each one: a name that starts with _, like _spare, tells the compiler the variable is unused on purpose. Clippy, the linter you'll run before every review, adds warnings of its own.

The shape of a program

{{code:t0_hello#hello}}
{{out:t0_hello}}
  • Every Rust program starts at a function called main. fn defines a function. The body sits in braces, { }, not under an indent. Indentation is for people; cargo fmt sets it for you.
  • let makes a variable. A line that does something ends with a semicolon.
  • println! prints a line. {ordered} inside the text is replaced by the variable's value, like an f-string.
  • fn boxes_needed(items: i64, per_box: i64) -> i64 is the function's signature: its name, each parameter with its type, and after -> the type it gives back. Every parameter must say its type. There are no default values, no keyword arguments, and no two functions with the same name, so boxes_needed(12, 5) always means one thing.
  • return 0; leaves the function early, as in Python.

The last line of boxes_needed has no semicolon and no return. This is the rule that trips everyone from Python. Rust code is made of statements, which do something and usually end in ; (a for loop, or an if whose branches produce no value, needs none), and expressions, which produce a value. 899 + boxes * 150 is an expression. So is if ... { full } else { full + 1 }: each branch produces a value, and the if produces whichever branch ran. A block's value is its last expression, if that expression has no semicolon after it. A function's body is a block, so its last expression is what it returns. Add the semicolon and the expression becomes a statement that throws its value away:

() is the empty value, pronounced "unit": what a block gives back when it has nothing to give. Python would return None here and you'd find out three functions later. Rust stops you at the line. return 899 + boxes * 150; would also work, but Rust code leaves the last line bare, and you should too.

Variables, mut and shadowing

{{code:t0_vars#vars}}
{{out:t0_vars}}
  • let ordered: i64 = 12; says the type. Usually you leave it out and the compiler infers it from how the variable is used. Your editor shows inferred types in gray, which is a good way to learn them.
  • Variables can't change unless they're declared let mut. Most values in a program are set once and never change, and when you see mut you know to watch that one. You met the error for this in set up.
  • let sku = sku.trim(); makes a new variable with the same name, which hides the old one. That's shadowing. It's how Rust code says "the cleaned-up version of this from now on" without inventing a name like sku_trimmed.
  • const is a fixed value with a name, written in capitals. Its type is always written out. Put rules like "five to a box" in one, at the top of the file, so the next person can find them.

A type is what kind of value something is, which decides what you can do with it: you can divide numbers and you can trim text, and not the other way round. Python checks types while the program runs, and only on the line that's running. That's called dynamic typing, and it's why "12" + 1 fails in Python only when that line is reached. Rust checks every type of every variable before the program runs, which is static typing. Each variable has exactly one type for its whole life. If you've used pandas, you've met the idea already: every column has a dtype, and int64 and float64 there are i64 and f64 here. Rust gives every variable one.

Integer division drops the fraction, rounding toward zero. Python's // rounds down instead, so -7 // 2 is -4 in Python and -7 / 2 is -3 in Rust. The remainder % follows the same rule, so it keeps the sign of the left side. Only 7.0 / 2.0, with floats on both sides, gives 3.5.

Rust never converts between number types on its own. An f64 total divided by a usize count, which is what every average looks like, doesn't compile:

{{failout:t0_mixed}}

The help line uses a word you'll see in errors long before ticket 3 teaches it properly. A trait is a named ability that a type can have. Div<usize> is the ability "can be divided by a usize", Display is "can be printed with {}", Ord is "can be put in order". A type implements a trait when it has that ability. So "the trait Div<usize> is not implemented for f64" reads as "an f64 can't be divided by a usize", and the list under it shows what does work: an f64 divided by an f64. Read every "trait X is not implemented for Y" error that way: Y can't do X, so either change the type or use a different operation.

You convert with as:

{{code:t0_numbers#cast}}
{{out:t0_numbers#3}}

as never fails, and that's the danger in it. 3.99 as i64 drops the fraction. 300 as u8 can't fit, so it keeps what fits and gives 44 (under the hood shows why 44). -1 as u32 gives four billion. Use as where nothing can be lost: a whole number into an f64 for an average (exact for any whole number up to about nine quadrillion, far past any count you'll have), or a small count into a bigger type. When a conversion can fail, use one that says so: u8::try_from(x) returns an error for 300 instead of guessing.

Two integer types don't mix either. A u32 quantity times an i64 price is three errors at once, because the compiler can't tell which one you meant to change. Convert the smaller type up to the bigger one before the arithmetic: i64::from(qty) * price, or qty as i64 * price. i64::from only exists for conversions that can't lose anything, which makes it the safer habit.

The ! means macro

println! isn't a function. The ! marks a macro: code that writes code. Before compiling, the compiler expands println!("{ordered} bolts", ...) into the longer code that does the printing. Macros exist for things a function can't do. A Rust function takes a fixed number of arguments of fixed types, and println! takes any number of any type. It also reads your format text while compiling, so a {} with no value to fill it, or a misspelled variable name inside the braces, is a compile error and not a surprise at run time.

A running program has two output channels. Standard output is for its results, and standard error is for messages about how it's going: warnings, errors, debugging. Both appear in your terminal. They separate when you send output somewhere: cargo run > out.txt puts standard output in the file and still shows standard error on screen, so a report file never fills up with complaints.

Formatting output

Rust's format codes are close cousins of Python's f-string codes, so most of what you know carries over:

{{code:t0_format#format}}
{{out:t0_format#1}}
  • {sku} names a variable. Unlike an f-string, it can only be a plain name, not an expression. For qty / 8, leave the braces empty and put the expressions after the text, in order: "{} boxes of {}", qty / 8, 8.
  • After a colon comes the spec. <10 left-aligns in 10 characters, >5 right-aligns in 5, ^5 centers. 05 pads with zeros. .2 means two decimals, and >8.2 combines them. A character before the alignment, as in *>8.2, is the fill.

Tuples, arrays and vectors

{{code:t0_collections#tuple}}
{{out:t0_collections#1}}
  • A tuple groups a few values of different types, as in Python. let (sku, qty, price) = line; unpacks it. line.0 is the first item: tuples use a dot and a number, not brackets.
  • An array has a fixed length that's part of its type: [u32; 5] is exactly five u32s. Useful for small fixed lists.
  • A Vec (vector) is Python's list: it grows, and all its items have one type. vec![...] makes one, and push adds to the end, which needs mut.

Reading items:

{{code:t0_collections#get}}

A position past the end doesn't raise an exception for a try block to catch. It stops the program. (Rust has a way to catch a panic, for special cases. It isn't error handling, and this course never uses it.) That's called a panic: the program prints where and why, and stops with exit status 101, a number that tells the shell it failed (under the hood has more).

References: & and *

A reference lets code look at a value without taking it. &qty is a reference to qty. Making one is called borrowing. Following a reference to the value it points at is written *:

for q in &qty borrows the list, so each q is a reference to a number, not the number. Arithmetic works on references to numbers, so first * 2 would also have compiled. Comparison doesn't:

Without the &, the loop takes the vector itself and uses it up, so it's gone afterward. That's called a move. Python never does this, and it's the idea at the center of Rust, which ticket 1 explains properly. For now: loop over &list unless you're finished with the list.

Some values don't move, because copying them is as cheap as moving them. Numbers, bool, char and &str are like that, and so is an array made only of them. Those types are called Copy: using one by value hands over a copy and leaves the original usable. So for q in qty over an array of numbers leaves qty usable after the loop. A Vec is never Copy, even a Vec of numbers, because it owns a block of memory stored elsewhere, so the loop in the error above moved it. A String is the same.

Structs and methods

A struct is a named group of fields, each with a type. It's the shape of one row of a DataFrame, with the column types written down, or a @dataclass if you've used one. An impl block ("implementation") holds the functions that belong to it:

{{code:t0_struct#struct}}
{{code:t0_struct#use}}
{{out:t0_struct}}
  • Self means "the type this impl is for", here Bin. new is a plain function that builds one. Rust has no constructors and no __init__; new is only a naming habit, and everyone follows it.
  • location: &str takes borrowed text, and .to_string() makes the bin its own copy, a String, to keep. Text, briefly explains the two text types.
  • In Bin { location: ..., capacity, on_hand: 0 }, a bare capacity is short for capacity: capacity.
  • A function whose first parameter is some form of self is a method. &self borrows the bin to read it. &mut self borrows it to change it. In Python nothing in a method's signature says whether it changes the object. Rust makes you say which, so the signature tells you whether a call can change the value. (A few special types, met much later, are the exception.) That's why bin must be let mut: put_away takes &mut self.
  • Bin::new(...) uses ::, because new belongs to the type and there's no bin yet. bin.put_away(30) uses a dot, because it's called on a value. In general :: walks into a type or a module (a named group of code, below), and . reaches into a value.
  • qty.min(...) is a method too, on u32. Numbers have dozens.
  • #[derive(Debug)] asks the compiler to write the code that makes {:?} work for Bin. Ticket 3 explains what else derive can write.

Maybe a value, maybe an error: Option and Result

Rust has no None that can turn up anywhere and no exceptions. Two types take their place, and you'll handle one of them on nearly every line of real code.

Option<T> is "maybe a T": either Some(value) or None. The <T> is a type parameter: Option<u32> is maybe a u32, Option<&str> is maybe some text. Vec<T> works the same way, which is why a list of SKUs is a Vec<&str>. You find out which one you have with match:

{{code:t0_option#option}}
{{out:t0_option#1}}

match lists the shapes a value can have, each followed by => and what to do. Some(sku) matches a value and names what's inside. The compiler checks that you covered every shape, so you can't forget None. if let Some(sku) = ... is a match for when you only care about one shape.

Result<T, E> is "a T, or an error of type E": Ok(value) or Err(error). Anything that can fail returns one, such as turning text into a number:

  • .expect("...") means "give me the value, and if it's an error, panic with this message". It's there for things that can't fail, and the message should say why.

Closures: doing something to every item

A Vec of your own structs is the Rust shape of a DataFrame: one struct per row. Picking a column, or the row with the biggest value, takes a small function that says what to look at:

{{code:t0_closures#closures}}
{{out:t0_closures}}
  • |item| item.qty is a closure: a function with no name, written where it's used. The parameters go between the bars and the body follows. Python's lambda item: item.qty is the same idea.
  • .map(...) runs the closure on each item and hands out the results, so .map(|item| item.qty) is the quantity column. .sum() adds it up.
  • .max_by_key(...) returns the item whose closure value is biggest, as an Option, because an empty list has none. On a tie it returns the last of the tied items.
  • Vec::new() makes an empty vector. The compiler works out what it holds from what you push, here &String, references to each item's SKU.

That's enough to use them this week. Ticket 1 explains closures properly, along with filter, count and the rest.

Text, briefly

Rust has two text types, and the difference matters from ticket 1 on. Text in quotes in your source is a &str: a borrowed view of text stored somewhere else, here inside the program file. Imports and the prelude

Reading the docs

You will spend more time in the documentation than in any book. The standard library's is at doc.rust-lang.org/std, and rustup doc --std opens a copy offline. Every published crate has its docs at docs.rs, and cargo doc --open builds the docs for your project and every crate it uses. Your editor's hover shows the same text for whatever is under the cursor.

On a type's page, such as Vec, the search box at the top finds anything by name. Below the description are the type's methods, then "Trait Implementations", which lists the things the type can do through traits. Ticket 3 shows how to give your own types traits. A method you can't find among the methods is often in there. A Vec also has every method of a slice, listed under "Methods from Deref<Target = [T]>": that's where first, last and get live. Each method starts with its signature, and reading one is a skill worth practicing:

  • pub fn push(&mut self, value: T) on Vec. pub means anyone can call it. &mut self means it changes the vector, so your variable needs mut. It takes one item of the vector's item type, T, and there's no ->, so it returns nothing. You know all that before reading a word of the description.
  • pub fn trim(&self) -> &str on str. It only reads the text, and it returns a borrowed view, so it doesn't copy anything.
  • pub fn split_once<P>(&self, delimiter: P) -> Option<(&str, &str)> on str, followed by where P: Pattern. Together those say the delimiter can be any type that can be searched for, such as a char or a &str. It returns maybe a pair of borrowed pieces: None when the delimiter isn't there.

Some signatures look worse than they are. get's is full of angle brackets because it accepts a range as well as a position. On a first read, skip what's inside the angle brackets and read the rest. One more piece of syntax you'll see in signatures and examples: _ means "something I'm not naming". In a match, _ => matches anything left over. let _ = ...; throws a value away on purpose. Vec<_> means "a vector of whatever the compiler works out". The symbol lookup at the end of this page lists every piece of punctuation in the course, for when you meet one and can't remember it.

When the compiler's help is wrong

The help line is right most of the time. It's a suggestion for making the code compile, though, not for making it correct, and a few suggestions compile while doing the wrong thing. Before you take one, check it against what you know. The ones in this course:

  • (total / count) as f64. It divides as integers first, dropping the fraction, then converts. Convert each side: total as f64 / count as f64.
  • (qty * price).into() for a u32 times an i64. The multiplication is what fails, so converting its result can't help. Convert qty before multiplying.
  • .to_string() when you compare a String with a &str. It compiles by copying the text every time. Compare my_string.as_str() with the &str instead. Ticket 1 explains why that works.
  • "consider removing the borrow". Taking the & off often turns a type error into a move error a moment later. When it does, the & was right and something else needs to change.
  • .clone(), suggested to get past a move or borrow error. It works by copying, and it hides the question the error was asking: who should own this value? Ticket 1 is about answering it.

Warm-up drills

Put drills in a program of their own. Cargo treats every file in src/bin/ as a separate program named after the file, so make src/bin/drills.rs with its own main and run it with cargo run --bin drills. Once there's more than one program, plain cargo run stops and asks which one you mean. Keep it running src/main.rs by adding default-run = "snippets" under [package] in Cargo.toml, the project's settings file. [package] starts a section, and each line under it is a setting. Before you type, answer these in your journal. What type is each field, and why? Which of the summary numbers need the list of lines walked once, and can one loop compute several of them? Stuck?

Hint 1: where the data lives

Build the five lines in main with your new function, inside vec![...] or an array. A method like fn line_cents(&self) -> i64 keeps the multiplication in one place, so the table, the total and the average all agree.

Hint 2: printing cents as dollars

53259 cents is 53259 / 100 dollars and 53259 % 100 cents. Print the cents with a spec that pads to two digits with zeros, or 90 dollars prints as 90.0. To make the dollars-and-cents pair fill a 10-character column, give the dollars part a width of 7: seven, plus the dot, plus two.

Hint 3: the biggest line

Keep a reference to the best line so far, starting with the first one, and replace it inside the loop when a line beats it. &lines[0] is safe here because you wrote five lines into the code yourself. Or use .iter().max_by_key(...) from closures, which keeps the whole line, SKU included, and handle the Option it returns with match or if let. Check what each way does on a tie.

Under the hood

Don't skip this one. Every later ticket assumes it.

Bits, bytes and integers

A computer stores everything as bits, each 0 or 1. Eight bits make a byte. A u8 is one byte read as a number in base 2: each bit is worth twice the one to its right, so 00000101 is 4 + 1 = 5. Eight bits have 256 patterns, so a u8 holds 0 to 255. A u32 is four bytes and an i64 is eight.

{{code:t0_bits#bits}}
{{out:t0_bits#1}}

Signed types like i8 use two's complement. The leftmost bit counts as minus its usual value, so in an i8 it's worth −128 instead of 128. All eight bits set is −128 + 127 = −1, and a lone left bit is −128. The payoff is that the processor adds signed and unsigned numbers with the same circuit. It also explains -1 as u32 above: as keeps the bits and changes how they're read, and all ones read as unsigned is the largest u32. 300 as u8 keeps only the lowest eight bits of 300, which is 300 − 256 = 44.

A fixed size means a sum can be too big to fit. That's overflow, and Rust gives you methods to choose what happens:

{{code:t0_bits#overflow}}
{{out:t0_bits#2}}

checked_add returns None when the result doesn't fit. wrapping_add goes round like a car's odometer: 250 + 10 is 260, minus 256 is 4. saturating_add stops at the maximum. A plain + that overflows panics in a debug build:

{{code:t0_panic#overflow}}
{{out:t0_panic#3}}

Built with --release, the same lines don't panic: the addition wraps, and it prints 4. That's a choice made for speed, and it's why code that adds up numbers from outside the program uses checked_add. (black_box only stops the compiler from noticing the overflow while compiling, which it otherwise would.) Python never overflows because its integers grow, and pays for that with speed and memory on every operation.

Memory is a long row of numbered bytes

While your program runs, its data lives in memory, which you can picture as one very long row of bytes, each with a number called its address. A variable is a name for a few bytes in that row. How many depends on the type:

{{code:t0_bits#sizes}}
{{out:t0_bits#3}}

A char takes four bytes because it can hold any single Unicode scalar value. Unicode gives every symbol in every writing system a number, a code point, and a scalar value is any code point outside a small reserved range. A reference such as &i64 is an address: eight bytes on a 64-bit machine, whatever it points at. That's also why usize is eight bytes here: it's defined as the size of an address, so it can count as far as memory goes. The addresses themselves change every run, because the operating system shuffles where a program's memory starts, as a defense against attacks. Ticket 1 shows where a Vec and a String keep their contents.

A value that holds an address is called a pointer, and a reference is a pointer with rules. Rust checks that every reference points at a live value. There is no null reference, the "points at nothing" value that crashes C and Java programs: where something might be missing, Rust uses Option, and the compiler makes you check.

Getting memory for a value is allocating it, and handing it back when you're done is freeing it. In C you free by hand, and freeing too early or twice is a classic crash. Python has a garbage collector, a part of the running program that finds values nothing uses anymore and frees them. Rust has neither. Every value has one owner, usually a variable, and when the owner's block ends at its closing brace, its scope ends and the value is dropped: freed, right there. That's the rule behind every borrow error you'll meet: a reference can't outlive the value it points at.

Text is bytes

Text is stored as numbers too. ASCII, from the 1960s, numbers 128 characters (English letters, digits, punctuation), each fitting in one byte. Unicode numbers every character in every script, about 150,000 so far. Each one's number is its code point. UTF-8 is the standard way to store code points as bytes: ASCII characters take one byte, as before, and everything else takes two to four. Rust's text is always UTF-8.

{{code:t0_text#utf8}}
{{out:t0_text#2}}

é is two bytes, 195 and 169, so café is four characters and five bytes. Python's len("café") is 4 because Python counts code points. Rust's .len() counts bytes, because that's what the computer stores and what it costs to copy, and .chars().count() counts chars, which are code points. (Those usually match what you'd call characters. Not always: an accent can be stored as its own code point after the letter, and some emoji are several joined together.) Since characters have different widths, finding the fifth one means reading from the start, so Rust won't let you write sku[0]:

{{fail:t0_strindex}}
{{failout:t0_strindex}}

.chars().next() gets the first character. &sku[..3] is a slice by byte position, which is fine for ASCII codes like SKUs and panics if the position falls in the middle of a character. Hand-typed data is full of characters you didn't expect, as ticket 4 finds out.

Your program is a process

A running program is a process. The operating system gives each one its own memory, the arguments it was started with, and a current working directory: the folder it counts as "here". A relative path like data/kettle_creek.db is looked up from that folder, not from where the source file is:

{{code:t0_cwd#cwd}}
{{out:t0_cwd}}

fn main() -> std::io::Result<()> lets main fail with a file-system error, and the ? after each call means "if this failed, stop here and pass the error on". Ticket 1 explains both. The program makes a folder with a file in it, then moves into the folder. The same relative path that found the file a moment ago finds nothing, because "here" changed. cargo run runs your program from wherever you typed it, so run it from the project folder, where data/ is. In Python the same thing happens, and it's why a notebook that works stops working when you move it.

When a process ends, it hands back one number, its exit status: 0 for success, anything else for failure. A panic exits with 101, as you saw above. Your shell keeps the last one:

cargo run --bin week0
echo $?

Schedulers and scripts read that number to decide whether your program worked. Ticket 6 makes your program set it on purpose.
