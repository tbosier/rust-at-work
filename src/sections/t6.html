One function for every table

Three of the four sheets are tables: a header row, then one row per item, each item a different type. You could write three nearly identical functions. This page shows how to write one, and how to give the program a command line that refuses bad input. First, the new crates:

A trait is a promise

A trait names a set of methods that a type promises to have. You've been using traits since ticket 1: Debug, Display, Ord and Iterator are all traits. Now you write one. Here is a trait for anything that can be one row of a table, on the library toy:

{{code:t6_trait#trait}}

headers has no self: it belongs to the type, not to any one row, because every book has the same columns. It's called an associated function, and you call it on the type, as Book::headers(), the same way you've called Bin::new since week zero.

Its return type, &'static [&'static str], reads from the inside out:

  • &str is borrowed text, and &[&str] is a borrowed list of those: a slice, as in week zero.
  • 'static is a lifetime, like ticket 3's 'a, but a fixed one: "good for the whole run of the program". It's the longest there is.
  • String literals such as "title" are &'static str, because they're stored inside the program file itself and never freed. A list written out of literals, &["book_id", "title"], is 'static too.

So headers can hand out its list without anyone owning it, and the caller can keep it as long as it likes. cells takes &self, so it's an ordinary method that reads one row. Implementing the trait is where each type keeps its promise:

{{code:t6_trait#impls}}

Python's nearest relative is a Protocol from typing, or an abstract base class. The difference is that Python checks a protocol only if you run a type checker, and only as a hint. Rust checks every use of the trait, at compile time, every time.

A word on .clone() in cells. Each cell becomes a new String because the trait says Vec<String>. That's a copy of every piece of text per row, which is fine for a few thousand rows in a report. A trait that hands a writer each cell directly, the way the ticket's sheets will need to anyway, avoids the copies. Notice that the trait's signature decides the cost for every type that implements it. Designing a trait means choosing that cost.

When the type isn't known until the program runs

A generic function needs one type per call: a &[Book] or a &[Loan], never a mix. Sometimes you need a list of different types side by side. That's a trait object, written dyn Trait:

{{code:t6_dispatch#dyn}}
{{code:t6_dispatch#mixed}}

Box<dyn Describe> means "a value on the heap, of some type that implements Describe, and we've forgotten which". The values have different sizes, so they can't sit side by side in a Vec directly. Each goes in its own Box on the heap, and the Vec holds the pointers. The cost is a heap allocation per item and an indirect call per method call. Under the hood shows what that call looks like.

Not every trait can be used this way. Try it with TableRow:

A trait object only knows a value, not its type. headers() has no value to ask, so there would be nothing to call it on. That's what "dyn compatible" means: every method has to be callable through a value, unless it opts out of trait objects with where Self: Sized, which is what the compiler's help above suggests.

For the pack, generics are the right fit. Each sheet holds one type of row, known when you write the code, and headers naturally belongs to the type. Reach for dyn when the set of types really is open or mixed at run time: plugins, a list of different shapes, error types from several libraries (that's what Box<dyn Error> in main has been doing since ticket 1).

  • Rows and columns are zero-based numbers: row 0, column 0 is cell A1. Rows are u32 and columns are u16, because a sheet has at most 1,048,576 rows and 16,384 columns, so as u32 on a loop index is normal here.
  • write_number stores a number. Excel numbers are f64, so your Cents becomes dollars at the last possible moment, for display only. All the adding up has already happened in integers. Writing a formatted string like "$1,204.50" instead would look the same and break Priya's SUM, which is the mistake the email is warning you about.
  • A Format is made once and passed by reference to every cell that uses it. "$#,##0.00;[Red]($#,##0.00)" is Excel's own number format language: the part before the semicolon is for positive numbers, the part after for negatives, here red and in parentheses, the accountants' convention.
  • set_freeze_panes(1, 0) freezes everything above row 1, so the header stays put when scrolling. autofilter takes the first and last row and column of the table, header included.
  • Almost every method returns a Result, because almost anything can be invalid: a sheet name over 31 characters, a row past the limit. ? handles all of them.

Failing like a good citizen

A program run by a person can print an error and stop. A program run by a scheduler has to say whether it worked in a way another program can check, and that's the exit status: 0 for success, anything else for failure. main can return std::process::ExitCode to choose it:

Stuck?

Hint 1: the shape of the trait

The wiki's cells returns Vec<String>, which loses the difference between text and numbers. Your sheets need that difference, because money must be written with write_number_with_format. So let the row write itself: a method that takes the worksheet, the row number and the money format, and writes its own cells. Look at what &mut Worksheet lets a method do.

Hint 2: rows that borrow

A discrepancy row needs the supplier's name, which lives in your suppliers Vec. Rather than cloning every name into a new struct, a small struct with a &'a Discrepancy and a &'a str can implement the trait. Implementing a trait for a type with a lifetime looks like impl TableRow for DiscrepancyRow<'_>. The '_ means "some lifetime, and I don't need to name it", because nothing in the impl has to say how it relates to anything else. Most of the time Rust works lifetimes out without being told, and '_ marks a spot where you let it.

Hint 3: no half-finished file

Do all the loading, parsing and reconciling first, and build the Workbook in memory. save is the only call that touches the output file, so if anything before it fails, nothing is written. Validate the month in clap's value_parser, and it fails before the database is even opened.

Under the hood

Generics and trait objects, compiled

When you call print_table(&books) and print_table(&loans), the compiler writes two copies of print_table, one with T replaced by Book and one by Loan. That's monomorphization, from "one shape". Each copy calls its type's cells directly, and the optimizer can inline it as if you'd written two separate functions by hand. The price is size and build time: a generic used with fifty types is compiled fifty times. (The optimizer may then inline some copies into their callers or merge identical ones, so the final count can be lower.) This is static dispatch, because which method runs is fixed when the program is compiled.

A trait object works the other way. The compiler builds one table per type, the vtable, listing that type's implementation of each method, and a &dyn Describe carries two pointers: one to the value and one to its type's vtable. A method call reads the function's address out of the vtable and jumps there. You can see the second pointer:

{{code:t6_dispatch#sizes}}
{{out:t6_dispatch#2}}

A fat pointer, twice the size of an ordinary reference. This is dynamic dispatch: one copy of the code, decided at run time. The optimizer usually can't see through the jump to inline it, though it sometimes works out which method it must be. For a monthly report, the speed difference between the two is far too small to measure. Choose by what the code needs to say: a fixed type per call means generics, a mixed collection means dyn. C++ templates and virtual functions make the same trade. Java's and Python's generics only give you the dynamic kind.

An .xlsx file is a folder of XML

Office Open XML, the format behind .xlsx, .docx and .pptx, is a ZIP archive of XML files. A one-fine workbook made the same way as the wiki's example, listed with unzip -l (dates and times blanked here):

Run unzip -l on your own pack. Look at a sheet's XML, and find your money: it's a plain number, which is why Priya can sum it. The format is an open standard, ECMA-376, so any program can read your pack, not just Excel.

Processes, streams and exit codes

Every program starts with three open streams: standard input, standard output and standard error. println! writes to standard output and eprintln! to standard error. In a terminal they both appear on screen, which is why they look the same. They go to different places as soon as anything is redirected: cargo run -- --month 2026-09 > log.txt sends output to the file and still shows errors on screen, and a scheduler can save each to its own log. Data on one stream and complaints on the other is what lets programs be chained with pipes without errors getting mixed into the data.

When a process ends it hands its parent one small number, the exit status. Shells keep it in $?, and && and || act on it: cargo run -- --month 2026-09 && echo sent only says "sent" on success. Cron, systemd, CI servers and every job scheduler in Part 2 decide success or failure by this number alone. They never read your message. A program that prints "error" and exits 0 has told the scheduler everything went fine. Conventions: 0 is success, 1 is a general failure, 2 is bad usage (clap's choice, and many Unix tools'), and a few higher numbers are reserved by shells, so stay below 126.
